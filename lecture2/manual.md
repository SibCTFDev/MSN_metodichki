## Теория: компоненты приложения

### IPC

**IPC** - inter process communication или взаимодействие между процессами. Крайне важный аспект Android-приложений с точки зрения исследователей безопасности. Рассмотрим компоненты, из которых состоит мобильное приложение Android и использующих IPC. Каждый компонент - входная точка, через которую система или пользователь может взаимодействовать с мобильным приложением.

Всего 4 компонента:
*   Activity
*   Services
*   Content Provider
*   Broadcast Reciever

У каждого приложения должна быть, как минимум, одна Activity

### Activity

**Activity** - это главный компонент в Android. Можно рассматеривать Activity, как базу, к которой крепятся все компоненты UI, которые вы видите на экране. Можно ассоциировать Activity с экраном, которой отображается на телефоне. Жизненный цикл Activity изображён на картинке, он отражает из каких состояний в какие может перейти приложение и при обстоятельствах. Состояния - это методы Activity, в которых разработчик может реализовывать бизнес-логику. Например, метод onCreate() должен отрисовывать интерфейс. Метод onStart() - например, реализовывать всплывающее окошко с приветствием пользователя. Метод onPause() - сохранять состояние игры, которое запущено у пользователя на экране.

С точки зрения исследователя безопасности нам наиболее интересны переходы в следующие состояния:
*   onCreate
*   onStart

Интерсны они по той причине, что мы, как нарушитель, можем явно влиять на те данные, который обрабатываются в конкретных методах этой Activity.

### Intent

**Намерение (Intent)** - это абстрактное описание операции, которая должна быть исполнена. Примерами использования intent'ов служат операции по выбору фотографий, отправки писем, совершения звонка, запуска браузера. В Android-приложениях многие операции работают через намерения.

Наиболее распространённый сценарий использования намерения - запуск другой активности в своём приложении. Также intent'ы можно использовать для запуска активности или сервиса, направленных на выполнение каких-либо действий. Намерения могут применяться для трансляции сообщений по системе. Любое приложение способно зарегистрировать широковещательный приёмник и отслеживать эти намерения с возможностью на них реагировать. Это позволяет создавать приложения, использующие событийную модель, в основе которой лежат внутренние, системные или сторонние события, передаваемые внешними программами.

Android транслирует намерения для объявления о системных событиях, например об изменениях в состоянии сетевого подключения или в уровне заряда батареи. Системные приложения в Android, такие как программы дозвона или управления SMS, регистрируют компоненты, отслеживающие заданные намерения, например _входящий звонок_ или _получено новое SMS-сообщение_, и соответствующим образом реагируют на них. Intent'ы бывают двух типов - явные и неявные. В явных (explicit) намерениях необходимо указывать класс приложения, which будет его выполнять. В неявных (implicit) намерениях, наоборот, указывать класс не нужно, их цель дать пользователю/системе выбор, какое приложение будет обрабатывать intent. В неявных намерениях необходимо указывать параметры `action`, `data`, `category`. Например, для открытие ссылки на новостной ресурс вам потребуется браузер, если браузеров будет установлено несколько, то система предложит выбрать один из них. Action - действие, которое будет выполнено приложением. Данные - это URI на те данные, которые будет обрабатывать компонент приложения, и тип MIME для этих данных. Так как разные Activity могут обрабатывать разные данные в зависимости от логики приложения. Категория - строка, содержащая дополнительную информацию о виде компонента, который должен обработать намерение. В объект **Intent** можно поместить любое количество описаний категорий. Extras - пара ключ-значение, передающие дополнительную информацию для завершения запрошенного действия. https://developer.android.com/guide/components/intents-filters

| `adb shell am start -a <intent-action> -n <package/.componentName e.g com.example.app/.ExampleActivity> -e <key> <value>` |

### Services/Сервисы

Службы (Сервисы) в Android работают как фоновые процессы и представлены классом **android.app.Service**. Они не имеют пользовательского интерфейса и нужны в тех случаях, когда не требуется вмешательства пользователя. Сервисы работают в фоновом режиме, выполняя сетевые запросы к веб-серверу, обрабатывая информацию, запуская уведомления и т.д. Служба может быть запущена и будет продолжать работать до тех пор, пока кто-нибудь не остановит её или пока она не остановит себя сама. Сервисы предназначены для длительного существования, в отличие от активностей. Они могут работать, постоянно перезапускаясь, выполняя постоянные задачи или выполняя задачи, требующие много времени.

| `adb shell am startservice -a <intent-action> -n <package/.componentName e.g com.example.app/.ExampleActivity> -e <key> <value>` |
| --- |

### Content Providers

Контент-провайдер или **"Поставщик содержимого" (Content Provider)** - это оболочка (wrapper), в которую заключены данные. Если ваше приложение использует базу данных SQLite, то только ваше приложение имеет к ней доступ. Но бывают ситуации, когда данные желательно сделать общими. Простой пример - ваши контакты из телефонной книги тоже содержатся в базе данных, но вы хотите иметь доступ к данным, чтобы ваше приложение тоже могло выводить список контактов. Так как вы не имеете доступа к базе данных чужого приложения, был придуман специальный механизм, позволяющий делиться своими данными всем желающим.

Поставщик содержимого применяется лишь в тех случаях, когда вы хотите использовать данные совместно с другими приложениями, работающих в устройстве. Но даже если вы не планируете сейчас делиться данными, то всё-равно можно подумать об реализации этого способа на всякий случай. Поставщик содержимого обязан имплементировать у себя CRUD-методы для доступа к данным - `insert()`, `update()`, `delete()`, `read()`. А также необходимо зарегистрировать поставщик содержимого в манифесте при помощи атрибута `provider`, указав атрибуты `name` и `authorites`. Authorites - URI путь для вызова поставщика провайдера и имеет вид: `content://<authorities path>/`

Запуск Content Prodiver'ов

| `adb shell content <query/insert/update/delete> --uri content://<path1>/<path2>` |

### Broadcast Receiver

Broadcast Receiver - приёмник широковешательных сообщений. Используется для того, чтобы получать сигналы от системы о происходящих событиях. Например, сигнал о низком заряде батареи или установке нового приложения. Приёмник широковещательных сообщений — это компонент для получения внешних событий и реакции на них. Инициализировать передачи могут:
*   другие приложения или службы
*   сама система
*   ваше собственное приложение

Ширковещательные сообщения можно разделить на две группы:
*   Неявная широковещательная трансляция (implicit broadcast) — сообщения рассылаются всем желающим, а не конкретно вашему приложению. Вам нужно только зарегистрироваться для получения этих сообщений через фильтр **IntentFilter** в манифесте. Система просматривает все объяленные фильтры намерений в вашем манифесте и проверяет, есть ли совпадение. Из-за этого поведения неявные широковещательные сообщения не имеют целевого атрибута
*   Явная трансляция (explicit broadcast) предназначена для конкретных приложений. В атрибуте **target** указывают имя пакета приложения или имя класса компонента, по которому можно найти получателя

Отправка широковещательных сообщений:

| `adb shell am broadcast -a com.example.intent.TEST  --es sms_body "test from adb"` |
| --- |

Начиная с Android 8 запрещается отправка неявных intent'ов - https://developer.android.com/develop/background-work/background-tasks/broadcasts.
